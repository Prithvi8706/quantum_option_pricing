## The fixed task and six evidence gates

Keep the original payoff, stochastic model, asset covariance, observation dates, notional, dollar tolerance and 99% per-price confidence. Keep the original tolerance grid; stricter or looser tolerances, portfolios and different financial models are separate experiments. Significant advantage still means a tenfold reduction in complete latency against the fastest eligible demonstrated classical method.

| Gate | Required evidence | What it permits |
|---|---|---|
| G0 Task and provenance | A frozen task contract, parameter/code/artifact hashes, environment, source-family identifier and prospective experiment rules | A comparable local experiment |
| G1 Arithmetic and source validity | An independent integer specification, signed/range/overflow checks, output XOR semantics, input/workspace restoration and compatible complete-source replay | Adoption of an exact change to the same digital financial source |
| G2 Complete financial error | Dollar bounds for law/discretization, tails, approximation, precision and synthesis; for compound/residual families also baseline, surrogate and exercise-policy regret terms; total error stays within the fixed tolerance | Adoption of changes to financial precision, loading law or approximation |
| G3 Estimator and confidence | An explicit estimator-specific normalization, source/inverse/iterate count, stopping rule and complete 99% failure allocation | A certified estimation schedule for the same source |
| G4 Classical comparison | Eligible methods with actual time-to-accuracy runs, reference-price checks, a declared coverage procedure and matched cold/warm accounting | A demonstrated comparator at the chosen tolerance |
| G5 Complete cost and crossover | One compatible G1–G4 construction, routing, state supply, protection, reaction timing, failure and simultaneous resource budget | A conditional L2 crossover or scoped budget miss under its stated hardware assumptions |

G5 is not a hardware advantage demonstration; that would require actual end-to-end execution and timing. A missing gate remains unknown, not zero cost. G2 is unnecessary for an exact replacement of the unchanged integer source; it becomes mandatory before claiming a continuous-model price or adopting changed law/precision.

The gates operate per source and contract. The latest **B4/B8 knock-out arithmetic** must not be multiplied by the earlier **C4/H8 controlled-residual estimator** counts. Heston and compound-option constructions also retain their own task and cost ledgers.

## Execution order without repeated run requests

Dependency cycles that merely represent mutual cross-checking must be split into an early interface check and a later integration check.

## The decision rule for every small experiment

Before a run, save its problem, candidate family, seeds/domain, comparator, error/failure allowance and acceptance condition. Prefer an algebraic/assumption check first, then a small implementation, then the required production-width and complete-source checks. Candidate families are bounded by each item's stopping rule; the default exploratory screen is at most four materially different candidates.

For exact circuit changes, acceptance requires identical signed integer behavior, arbitrary initial output XOR, clean workspace and preserved inputs, plus a real improvement at the declared resource budget. A resource tradeoff is a Pareto point, not automatically the new default. For approximate changes, require their G2 bound and price the corresponding G3 changes as well. For hardware alternatives, require a compatible gate set, finite cost/error inputs and simultaneous data/factory/routing capacity.

For expensive follow-up prioritization, use these **planning thresholds**, not claims about physics: prefer candidates with a plausible full-source depth reduction of at least 2%, or at least 10% fewer T gates or live qubits. Smaller exact changes can still be retained when cheap, independently verified and useful to later interfaces. A zero-cost or optimistic-bound calculation can reject a direction as insufficient at a stated operating point; it cannot certify achievable speedup.

Initial exploratory work is limited to 30 CPU-minutes per candidate and available local memory. This cap does not truncate a required correctness, confidence or time-to-accuracy run and call it complete. A validation that exceeds the exploratory budget receives a recorded run estimate, checkpoint and a scheduled local follow-up if worthwhile. If local resources cannot support it, mark the branch resource-limited and continue independent work. Use available CPU workers conservatively; GPU arms run only on an already available eligible local device.

After each experiment, write one of five decisions:

- **Accepted component:** all applicable checks passed; save the implementation and remeasure compatible combined costs.
- **Rejected candidate:** a stated correctness, assumption, error, resource or cost condition failed; save the counterexample/result and take the specified fallback.
- **Conditional branch:** a precise proof or interface is missing; name it and its next bounded test.
- **Different task:** a worthwhile variant changes the financial/output contract; keep it out of the original comparison.
- **Completed audit:** the accounting or evidence issue is resolved, without inventing an algorithmic speedup.

“Component accepted” does not automatically mean “entire limitation solved.” An item closes only when its declared scope and acceptance conditions are met. New breakthroughs can reopen a rejected branch, but routine continuation does not rerun the same failed candidate.

## Local receipts and progress memory

Use the existing pinned environment `.context/frontier_t0_env/Scripts/python.exe`. Write each new run to `results/limitation_program_20261001/<item>_<unique-run>/`; never reuse an archived output root. Each receipt contains:

- `protocol.json`: prospective task, hypothesis, candidate, tests, cost boundary and acceptance rule.
- `result.json`: actual outputs, before/after resources, failures and the declared decision.
- `verification.json`: executed commands, environment, test/proof checks, hashes and qualifications.
- `NEXT.md`: the next exact action, required inputs, fallback and reason for continuation or closure.

`implementation_plan/roadmap.json` is the initial plan, not an execution receipt. The first execution creates a separate `progress.json` in the new result program root. Track active item/substep, run directory, accepted baseline, decision, supplied dependency interfaces and unresolved gates. Update progress after every small result so an interrupted session resumes from evidence rather than from conversational memory. Append an outcome to the checklist; do not erase failed attempts or turn an unfinished task into a checkmark.

## Autonomy and completion

The execution policy carries forward the user's authorization for local testing. Within that scope, choose routine implementations, run the relevant checks, record the decision and continue to the next eligible substep without asking “is this good?”, “what is left?” or “shall I run the next test?”. Give brief progress updates about findings and changes of direction. Keep all files, experiments and results local. Do not push, publish, upload project data, create a PR, or use paid/cloud quantum hardware.
